Phase 0 — Discovery

Discovery — connectivity, schema and parameter checks run before the scored suite.

How this test works — what, how, dataset & metrics

What it measures

A pre-flight, go/no-go health check that runs before any scored test. It confirms the gateway is reachable, the STT and TTS request/response schemas are what the client expects, parameters behave, and real synth/transcribe round-trips succeed. Nothing here is scored — it decides whether the rest of the suite can run at all, and records exactly what the deployment supports.

How the code does it

Discovery runs as a sequence of isolated sub-checks, each wrapped so one failure can't abort the others. Every sub-check targets one concern:

What each sub-check does

Connectivity — Opens the gRPC channel (and REST where available) and times a round-trip, so a dead or mis-authenticated endpoint fails here rather than 40 tests later.

STT schema — Transcribes one known clip and checks the response carries the fields the client relies on — transcript, confidence, and per-word timings.

Streaming schema — Runs the same clip through StreamingRecognize and confirms partial results and a time-to-first-word arrive.

TTS schema — Synthesises one short utterance and checks audio comes back with the expected sample rate and streaming first-byte timing.

Parameters — Probes which request fields the gateway actually honours — accepted sample rates, and whether SSML changes the audio or is silently ignored.

STT features — A fast accept/honour snapshot for the serving-layer flags (word timestamps, n-best, word boosting, profanity filter, diarization); tests 1.14–1.18 measure these in depth.

Smoke tests — A handful of end-to-end synth-and-transcribe round-trips to catch gross breakage before scoring begins.

Language acceptance — Summarises the full STT language matrix — which of the advertised locales return usable text.

Test 1.1 — Clean-Speech Accuracy

How accurately the model transcribes clean, read English speech across eight standard benchmarks.

How this test works — what, how, dataset & metrics

What it measures

The baseline accuracy test. It plays clean English audio from well-known public corpora and compares the transcript to the reference, so you can place the model against published numbers.

How the code does it

Clean English clips are streamed to the model over gRPC and the returned transcript is compared to the dataset's reference text. Before comparing, both strings pass through Whisper's EnglishTextNormalizer, which expands numbers and currency, fixes contractions and strips casing and punctuation so only genuine word errors count. The two cleaned word sequences are then lined up by edit distance (jiwer): WER = (words substituted + inserted + deleted) ÷ reference words, with MER and character-level CER reported alongside. Each of the eight benchmarks is scored separately and gets its own PASS/warn verdict, and a raw cased-and-punctuated WER is also reported so the un-normalised picture is visible too.

Test 1.12 — Multilingual Accuracy

Multilingual accuracy — WER/CER per language for the model's supported languages.

How this test works — what, how, dataset & metrics

What it measures

Measures transcription accuracy language by language (not just English), using a common multilingual benchmark so languages are comparable.

How the code does it

For each language the harness pulls up to 200 clean read-speech clips from FLEURS and sends each one to the model, getting back a predicted transcript. Before anything is counted, both the correct reference text and the model's transcript are run through the same text normaliser (Whisper's — the English one for English, the basic one for every other language): this lowercases, strips punctuation and standardises spacing, so differences in formatting don't count as mistakes — only genuinely wrong words do. The two cleaned strings are then compared by edit distance. For space-separated languages the score is WER = (words substituted + inserted + deleted) ÷ (number of words in the reference); a WER of 0.15 means roughly 15 words in 100 were wrong. Chinese, Japanese and Thai have no spaces between words, so they are scored the same way but per character (CER) after all spaces are removed — this endpoint emits one space per character, and counting those would otherwise push the score toward 1.0. Each clip is scored individually; the per-clip scores are averaged into the language's number, with a bootstrap confidence interval, and compared against PASS/FLAG/FAIL thresholds. Every language is reported on its own line — there is deliberately no blended macro-average, because the languages span very different difficulty tiers and one combined number would hide more than it shows.

Note

Why the Metric column is mixed, and why Korean is CER. WER (word error rate) needs word boundaries, which it finds by splitting on spaces — so it is used for the space-separated languages here (English, German, Vietnamese, and the rest). Japanese and Chinese (Mandarin) write text as an unbroken run of characters with no spaces, so a word-level rate is meaningless — a single wrong character would score the whole line as one bad 'word'. Korean does use spaces, but we score it by CER too, matching NVIDIA's model card ("Japanese, Korean, and Mandarin are evaluated using CER"): Korean spacing (띄어쓰기) is highly variable and its inflectional word-endings make WER punish near-correct words as whole-word errors — Korean scored ~26% by WER but ~10% by CER (card: 7.3%). CER is the identical edit-distance math, counted per character after whitespace is removed. Greek is left out entirely: the card places it in the adaptation-ready tier with no published score, and our ~50% WER reflects a language the model isn't tuned for — see the note under the table.

Test 1.8 — Domain Vocabulary

Domain vocabulary — accuracy on jargon-heavy speech and how well key terms and named entities are recognised.

How this test works — what, how, dataset & metrics

What it measures

Measures performance on specialised content (finance, meetings) where rare terms and proper nouns matter more than overall WER.

How the code does it

On jargon-heavy speech, overall WER hides what matters, so this zooms in on the hard words. It computes domain_wer (WER on the specialised clips), a key-term recall rate (KRR — of the domain terms and named entities present in the reference, how many the model got right) and NE-WER (error rate restricted to named entities only). It also surfaces the most-frequently-misrecognised terms, so you can see exactly where the vocabulary breaks down.

Test 1.9 — Output Quality

Output quality — how well the transcript handles punctuation, capitalisation and numbers.

How this test works — what, how, dataset & metrics

What it measures

Clean words aren't enough: this checks the formatting that makes transcripts readable — sentence punctuation, proper capitalisation and correctly written numbers.

How the code does it

Beyond getting words right, a usable transcript needs correct formatting, so this scores three things against formatted references. Punctuation is scored as an F1 per mark — the precision and recall of each '.', ',', '?' and so on, so both missing and spurious marks count. Capitalisation accuracy checks the right letters are upper-cased, and is reported N/A for scripts with no case (CJK/Thai) rather than a false zero. Number accuracy checks digits are written correctly, reported N/A for native-digit scripts. Per-language runs use language-aware punctuation sets (Spanish ¿¡, CJK 。、, Arabic ؟،).

Test 1.5 — Noise Robustness

Noise robustness — how accuracy degrades as background noise gets louder, across four noise types.

How this test works — what, how, dataset & metrics

What it measures

Mixes clean speech with real-world noise at controlled signal-to-noise ratios and tracks WER as conditions worsen — a stress test for noisy rooms, cafés, streets and babble.

How the code does it

Clean speech is mixed with noise at a fixed signal-to-noise ratio (SNR — higher dB means quieter noise) and then transcribed, so you can watch accuracy fall as conditions worsen. Four noise types are used: synthetic Gaussian hiss plus real babble (MUSAN) and street and office recordings (DEMAND), each injected across SNRs from −5 to +20 dB. For every (noise type, SNR) pair it scores WER exactly as Test 1.1 does, and reports delta_rel — the percentage increase in WER versus the clean baseline — so the degradation curve is easy to read.

What it measures

Checks whether the model treats speakers of different accents equally by scoring the same kind of speech across many accent groups and measuring the spread.

What it measures

An operational check that the service tolerates the audio formats real clients send — different container/codec, sample rate, bit depth and channel layout — rather than only one golden format.

Test 1.3 — Streaming Performance

Streaming responsiveness — how quickly partial and final words arrive during live transcription.

How this test works — what, how, dataset & metrics

What it measures

Measures the live-dictation experience: how soon the first word appears, how long results take to finalise, how stable partial hypotheses are, and whether streaming hurts accuracy.

How the code does it

The clip is streamed in small chunks and every partial and final result from StreamingRecognize is timestamped. From those timestamps the test derives time-to-first-word (how soon any text appears), finalisation latency (how long after the audio ends the final text arrives) and partial latency. A stability rate measures how often an interim word survives unchanged into the final transcript — jitter-free streaming scores near 1.0. The same audio is also transcribed in batch and the WER compared, so you can see whether streaming costs accuracy. English-only: streaming timing is a property of the serving stack, not the language.

What each sub-check does

Time-to-first-word (TTFW) — How long after audio starts streaming until the very first word of text comes back. This is the number a live caption or dictation user feels as 'lag before anything appears' — our P50 is 0.97s, but the P99 tail reaches ~2.3s on the slowest clips.

Finalization latency — After the audio ends, how long until the result stops changing and the transcript is declared final. It measures the tail of the stream — the wait between 'done speaking' and 'text locked in' (P50 ~0.17s here, very tight).

Partial latency — The gap between consecutive interim (partial) hypotheses while speech is still arriving — i.e. how often the on-screen text refreshes. Lower means smoother, more responsive live updates (P50 ~0.06s — updates roughly 16×/second).

Stability rate — Of the interim words the server shows mid-stream, the fraction that survive unchanged into the final transcript. High stability means text doesn't flicker or rewrite itself as you speak; jitter-free streaming scores near 1.0 (here 0.95).

Streaming RTF (×realtime) — Real-Time Factor for the streaming path: processing time ÷ audio duration. At/under ~1.0 the model keeps pace with live audio; above 1.0 it falls behind. A ratio, not a latency, so it is kept off the seconds axis and shown as its own tile.

Batch vs stream WER — The same clips are also transcribed in one-shot batch mode and the Word Error Rate compared. A near-zero gap (both 3.3% here) means streaming buys responsiveness without costing accuracy.

Test 1.10 — Confidence Calibration

Confidence calibration — whether the model's confidence scores actually track its accuracy.

How this test works — what, how, dataset & metrics

What it measures

A trustworthy model should be confident when right and unsure when wrong. This test checks that the reported confidence means what it says.

How the code does it

A confidence score is only useful if it tracks whether the model was actually right. Each recognised word is labelled correct or not by aligning the transcript to the reference (after lowercasing and stripping punctuation, so case and punctuation differences are not counted as errors), then bucketed by its confidence. Expected Calibration Error (ECE) is the average gap between a bucket's stated confidence and its measured accuracy (0 = perfectly calibrated). AUROC measures how well confidence alone separates right from wrong words (0.5 = useless, 1.0 = perfect error detector). The Brier score is the mean squared error of confidence-as-probability. A per-bin reliability curve is plotted against the ideal y=x line.

What each sub-check does

Per-word confidence — Each clip is transcribed with word timings enabled, and the model's confidence is read for every returned word. When the gateway returns per-word confidences those are used directly; otherwise the single utterance-level confidence is applied to each word as a fallback.

Correctness labelling — The transcript is aligned to the reference word-by-word. Matched words score 1 (correct); substitutions and inserted words score 0. Both sides are first lowercased and depunctuated so 'April,' vs 'APRIL' counts as a match — without this normalisation the all-caps reference corpus would mark nearly every word wrong.

Reliability curve — Words are dropped into ten confidence buckets (0.0–0.1 … 0.9–1.0). For each bucket the measured accuracy (fraction actually correct) is plotted against the bucket's mean confidence. A perfectly calibrated model sits on the diagonal; points below the line are over-confident, above are under-confident.

ECE (calibration gap) — The bucket-size-weighted average distance between stated confidence and measured accuracy — one number summarising how far the curve strays from the diagonal. 0 is perfect.

AUROC (error ranking) — Treats confidence as an error detector: how often a correct word outranks an incorrect one by confidence. 0.5 means confidence carries no signal; above 0.5 means low confidence genuinely flags likely errors.

Brier score — Mean squared error of confidence read as a probability of being correct — a single accuracy-and-calibration penalty where lower is better.

Deletion rate — Reference words the model dropped entirely (no hypothesis token). These have no confidence to score, so they sit outside the curve and are reported separately as a blind spot confidence cannot cover.

Test 2.3 — Prosody

Prosody — pitch variation, rhythm, pausing and speaking rate of the synthetic voice.

How this test works — what, how, dataset & metrics

What it measures

Flat, robotic speech is unpleasant even when intelligible. This measures expressiveness: pitch movement, rhythmic variation, pausing and tempo.

How the code does it

Intelligible speech can still sound flat and robotic, so this measures expressiveness directly from the audio — no reference recording required. It extracts the pitch (F0) contour and reports its standard deviation and range (how much the voice moves), an acoustic nPVI that captures rhythmic variation between successive voiced segments, the pause ratio (share of silence) and the speaking rate in words per minute. Together these flag monotone or unnaturally paced output. The intrusive 'F0 versus a reference' metrics aren't computable for a fixed synthetic voice — see 2.4.
